# Используемый алгоритм MTMCT

Описание актуального офисного запуска `run_hackaton_experiment.py` с
`PLAN_SETTINGS`. Это offline-обработка: сначала извлекаются локальные треки
всех камер, затем рассчитываются глобальные связи.

**Цепочка:** видео → YOLO → фильтрация боксов → ByteTrack → OSNet и галереи →
кандидаты → оценка связей → проверка конфликтов и конкурентов → Global ID →
эпизоды, карта, CSV/JSON и мозаика.

## 1. Детекция и локальные треки

YOLO26l обнаруживает людей: `conf=0.10`, `imgsz=1536`, шаг обработки 2 кадра.
ByteTrack запускается независимо для каждой камеры. Лупа выключена.
До трекера исключаются люди на экране, слишком маленькие боксы и вложенные
дубли головы/тела; отдельно отбрасываются боксы, охватывающие двух ранее
отслеживаемых людей. Минимальные размеры в долях исходного кадра:

| Камера (1–5) | Ширина | Высота |
|---|---:|---:|
| 3 | 0.024 | 0.10 |
| 5 | 0.020 | 0.09 |

Сохраняются bbox, кадры, уверенность, признаки и Local ID. Короткие разрывы
локального ID восстанавливаются по внешности и положению. Для разрыва
`0 < Δt ≤ 1.8 с` требуется cosine среднего ReID не ниже 0.62 при `Δt ≤ 0.5 с`,
иначе 0.70, и смещение центров не более `h·(0.30 + 0.20Δt)`, где `h` —
максимальная высота двух граничных боксов. Для одновременных дублей действуют
дополнительные проверки вложенности и длительности перекрытия.

Разрывы 1.8–4 с дополнительно проверяются по совместной стоимости:
`C_occ = 0.75·(1−(m+g₃)/2)/2 + 0.25·(1−exp(−0.5(d/0.35)²))`.
Здесь `d` — смещение нижней центральной точки в высотах бокса.
Требуются `m ≥ 0.70`, три независимых сравнения с `g₃ ≥ 0.67`, качество ≥ 0.30,
сопоставимые размеры боксов, `d ≤ 0.35` и `C_occ ≤ 0.11`.
Конкурирующие продолжения и физические конфликты проверяются отдельно.

Групповой артефакт — короткий широкий трек рядом с двумя предшествующими людьми,
перекрывающий другой трек — помещается в `artifact_candidate`: сохраняется
в диагностике, но не публикуется отдельной личностью. Это эвристический карантин.

## 2. Время и признаки

Время переводится в общую шкалу с учётом FPS каждой камеры и её смещения:

$$t_c(f)=\mathrm{PTS}_c(f)+\delta_c
\quad\text{или, если PTS отсутствует,}\quad t_c(f)=f/FPS_c+\delta_c.$$

OSNet IBN x1.0 извлекает 512-мерные L2-нормированные векторы человека:

$$e=\frac{v}{\|v\|_2},\qquad s(e_i,e_j)=e_i^\top e_j.$$

Трек хранит агрегированный embedding, кадры галереи и до четырёх прототипов.
Качество crop учитывается эвристически; перед отбором оно дополнительно
уменьшается на множитель `1 − 0.5·occlusion_proxy`. В галерею оценки допускаются
образцы с `q ≥ max(0.20, 0.35q_max)`. Прототипы выбираются по качеству и разнообразию.
Начало, середина и конец галереи сравниваются во всех сочетаниях; эти оценки
сейчас служат диагностикой, а не самостоятельным слагаемым итоговой стоимости.

## 3. Сходство внешности

### Как именно собираются и хранятся признаки

В трекинге есть два отдельных буфера: до **20 лучших crop по качеству**
(`feature_vectors/frames/quality/details`) и временная выборка до **256**
образцов (`temporal_vectors/frames/quality`), которая прореживается при заполнении.
Временная выборка используется при анализе устойчивых смен внешности/разбиении
треклета. Начало/середина/конец в `scoring.py` строятся из отобранной галереи,
а не из всех кадров исходного трека: это ограничивает временное покрытие.

Качество crop и агрегированный вектор:

$$q=c_{det}\,b\,(0.5a+0.5l),\qquad
\bar e=\frac{\sum_n q_ne_n}{\left\|\sum_n q_ne_n\right\|_2},$$

где `a=min(area/(256·128),1)`, `l=min(Var(Laplacian)/500,1)`,
`b=0.5` для обрезанного границей crop, иначе `b=1`.
Агрегирование использует лучшие сохранённые образцы. Отдельно сохраняется
`embedding_mean` по всем извлечённым векторам; основной scoring читает `embedding`.
При выборе до четырёх прототипов приоритет равен
`0.75q + 0.25·min((1−cos(e,p))/2)` относительно уже выбранных прототипов.

Кэш JSON позволяет повторять ассоциацию без YOLO/OSNet. SQLite-реестр каждого
прогона хранит ID, ревизии, связи и подтверждённые прототипы. Отдельный
`runs/office_identity_bank.sqlite` сопоставляет подтверждённые группы с памятью
между записями (`similarity ≥ 0.92`, отрыв ≥ 0.04) и обновляет близкие прототипы
при cosine ≥ 0.95:

$$p'=\frac{sp+qe}{\|sp+qe\|_2},\qquad s'=s+q.$$

Однако банк вызывается **после текущей ассоциации**: его результат записывается
в `persistent_person_ids`, но не исправляет текущие Global ID и не пересчитывает
рёбра графа. Это работающая память прототипов, пока не полноценный поиск
личности по памяти внутри основного сопоставления. В опубликованных папках
сохранены реестры прогонов; общий банк между записями в эти снимки не включён.

Пусть `m` — cosine агрегированных embedding, `g` — лучшее совпадение галерей,
а `p` — среднее трёх лучших сравнений HSV-гистограмм верхней/нижней одежды.
В стандартном офисном режиме, когда доступны все признаки:

$$S_{ReID}=0.75m+0.25g,\qquad S=(1-\lambda_p)S_{ReID}+\lambda_pp.$$

В актуальном режиме `λ_p=0.30·r_p`. Надёжность цвета `r_p` зависит от качества
crop, экспозиции, формы бокса, отличия центральной области от её краёв и
стабильности цвета между собственными образцами трека. Это консервативная
эвристика видимости, а не уверенность модели сегментации человека.

При отсутствии одежды используется только `S_ReID`; доступные ReID-компоненты
перенормируются по сумме их весов. Дополнительно рассчитывается `g_3` — среднее
до трёх лучших пар кадров, выбранных жадно без повторного использования одного
исходного кадра. Поэтому `g` и `g_3` — разные показатели. Соседние кадры всё ещё
могут быть похожими: отдельной гарантии независимости ракурсов нет.

## 4. Кандидаты и итоговая стоимость

Кандидаты ищутся KD-tree по средним векторам и прототипам, с `top_k=12`.
Добавляются короткие локальные продолжения и все пары с пересечением времени
на известных перекрывающихся камерах. Неизвестная топология не означает запрет.

Для доступных модальностей `k ∈ {appearance, space, time}`:

$$d_a=\frac{1-S}{2},\qquad
\alpha_k=\frac{w_kr_k}{\sum_{\ell\in A}w_\ell r_\ell},\qquad
C_{ij}=\sum_{k\in A}\alpha_kd_k.$$

Здесь `A` — доступные свидетельства, `r_a=√(q_iq_j)`, остальные надёжности
задаются пространственной/временной проверкой. Базовые веса офиса:
`(w_a,w_s,w_t)=(0.92,0,0.08)`. Геометрия ассоциации выключена. При отсутствии
измеренной временной оценки получается `α_a=1`, то есть `C=(1−S)/2`.
Разрешённая одновременность сама по себе не даёт временную стоимость ноль с
положительным весом. `C` — эвристическая стоимость, не вероятность совпадения.

Обычная межкамерная связь требует:

* `m ≥ 0.72` и `g_3 ≥ 0.67`; для последовательных непересекающихся наблюдений
  допускается `m ≥ 0.67` и `g_3 ≥ 0.72`;
* качества каждого трека не ниже 0.30 и хотя бы двух пригодных образцов,
  либо одного достаточно качественного представления (`quality ≥ 0.75`);
* `S ≥ 0.45`, `C ≤ 0.40`, суммарной надёжности не ниже 0.12;
* при неизвестной топологии дополнительно `S ≥ 0.55`; для положительного
  временного разрыва требование плавно растёт:
  `S ≥ 0.55 + (0.88−0.55)·min(Δt/60,1)`.
  Недостаточно поддержанная связь остаётся гипотезой. При разрыве более
  60 секунд для повторного узнавания личности требуется `S ≥ 0.88`.

Это условия основной стадии; локальное восстановление и стадия поддержки
несколькими камерами имеют отдельные правила ниже.

## 5. Назначение и глобальный граф

Для перекрывающихся камер Hungarian matching выполняется на интервалах с
постоянным составом треков. Поэтому одному непрерывному треку могут соответствовать
несколько последовательных фрагментов другой камеры. Используется оценка:

$$M_{ij}=S_{ij}+b_{ij},\qquad
b_{ij}=0.05\min(1,\tau_{ij}/3)\sqrt{q_iq_j},$$

где `τ` — длительность пересечения интервалов треков в секундах. Бонус ограничен
и экспериментален. Вариант «нет пары» имеет оценку 0.45; исходное сходство ниже
этого порога не спасается бонусом. Проверяются взаимный лучший выбор и отрыв
не менее 0.02 от конкурентов, включая «нет пары». Однозначное назначение
подтверждается только при сильном ReID, якорных треках и совместимости компонентов;
иначе сохраняется гипотеза `provisional` с отдельными Global ID.

Основной оптимизатор — агломерация с DSU, а не глобальный correlation clustering.
Сначала восстанавливаются локальные продолжения, затем подтверждаются якорные
рёбра и рассматриваются остальные присоединения. При обычном выборе рёбер
проверяется отрыв стоимости от физически несовместимых альтернатив (`margin=0.006`).
Перед объединением проверяются **все пары** участников двух компонентов:
одновременные разные люди одной камеры, запрещённые переходы и другие жёсткие
конфликты не допускаются. Локальные дубли имеют отдельное исключение.

Предварительные присоединения не объединяют DSU в `PLAN_SETTINGS`.
Слабый промежуточный трек может быть подтверждён при согласованной поддержке
**двух разных камер** уже собранной группы: на каждой связи `m ≥ 0.62`,
`g_3 ≥ 0.55`, `S ≥ 0.45`, `C ≤ 0.40`, разрыв не более 10 секунд,
качество трека ≥ 0.30, отсутствие конфликтов и неоднозначного конкурирующего
компонента. Неизвестная топология здесь разрешает рассмотрение, но не даёт бонуса.

## 6. Результаты и карта

Группы с суммарным наблюдаемым временем менее 1 секунды не публикуются.
SQLite хранит ревизии, устойчивые ID и события merge/split; отдельный банк
сохраняет подтверждённые прототипы. Предварительные связи экспортируются отдельно.
Личность и эпизод различаются: при отсутствии наблюдений **более 60 секунд**
создаётся новый `global_track_id = person_id:episode`. Обычный `global_id`
может сохранять личность после такого разрыва.

Для приблизительной 2D-карты нижняя центральная точка бокса переводится
гомографией камеры на план:

$$[u,v,1]^\top\sim H_c[(x_1+x_2)/(2W),\;y_2/H,\;1]^\top.$$

После деления на третью координату получаются нормированные координаты плана.
Опорные точки заданы вручную; эта карта не участвует в текущей ассоциации
личностей и не является метрически точной калибровкой.

Итог: `global_tracks_2d.csv`, `global_track_episodes.*`, `global_ids.json`,
`association_edges.json`, `provisional_links.json`, `identity_registry.sqlite`,
`floor_tracks.*` и `mosaic.mp4`.

Основные файлы реализации: `tracking.py`, `corridor_zoom.py`, `reid.py`,
`scoring.py`, `candidates_v2.py`, `overlap_matching.py`, `identity_v2.py`,
`identity_store.py`, `episodes.py`, `floor_map.py` и `visualize.py`.

Запуск из корня: `python run.py office --seconds 120 --run-name office_new`.
