## Состояние

Пять оригинальных видео и план загружены в локальный интерфейс:
`Офис — оригиналы 5 камер (ожидает обработки)`.
Все пять изображений камер проверены в браузере. Сетка по умолчанию — 3 колонки,
количество камер определяется данными. Схематические метки C1…C5 перенесены с
пользовательского рисунка; это не геометрическая калибровка.

| 3 | 2592×1944 | 25 | 1200.12 | H.264 |
| 4 | 2592×1944 | 20 | 1200.05 | HEVC |
| 5 | 2592×1944 | 25 | 1200.08 | H.264 |

Часы в кадре и начало контейнерных потоков отличаются. Временные смещения пока 0:
это просмотр от начала файлов, а не подтверждённая физическая синхронизация.
Одинаковое ограничение кадров даёт разные интервалы для 20 и 25 FPS.

Пользователь разрешил использовать самую свежую доступную версию, если отдельной
новой версии на GitHub нет. После повторного fetch Sevsese-Branch осталась на
0c3a32e; интерфейс и адаптивные расширения уже содержат этот код. Используется
существующий baseline YOLO26l / 1920 / OSNet, без подмены алгоритма.

Для демонстрации интерфейса обрабатывается короткий участок: камеры 1–2 по 30 с
(готовый кэш), камеры 3–5 по 10 с. Итоговое демонстрационное видео показывает
общие первые 10 с. Это не полный прогон 20-минутных записей и не benchmark точности.
Фактические ограничения каждого потока сохранены в manifest/config/performance.

Для обычного запуска в UI добавлено ограничение в секундах (по умолчанию 30),
независимо от FPS камеры. 0 отключает ограничение; ограничение кадров можно
использовать дополнительно, тогда действует более короткое из двух.

На этом компьютере встречалась нехватка системной памяти при одновременной сборке
frontend и инференсе 2592×1944. Worker ограничивает вычислительные потоки и не
загружает тяжёлые модули в координирующий процесс. Завершённые камеры можно повторно
использовать с опцией resume в worker JSON; кэш проверяется перед использованием.

Пользователь явно согласовал черновую визуальную привязку. Точки в локальном
`data/office_original/draft_floor_points.json` оценены по картинкам, не измерены.
Они используются только для демонстрации карты и не передаются ассоциации.

## 2D-карта

На странице «План помещения» выберите камеру → «Привязать к плану».
Выберите удобное время кадра и отметьте минимум четыре пары одних и тех же точек
**пола**: сначала на кадре, затем на плане. Покройте всю нужную область. Сохраните
привязку и повторите для остальных камер. Поддерживается до 20 пар на камеру.
Коллинеарные/неконечные и противоречивые соответствия отклоняются.

После появления наблюдений карта показывает нижнюю середину bbox, спроецированную
в нормализованные координаты плана, с цветом исходного Global ID. Есть выбор ID,
таймлайн, воспроизведение, история последних 15 с, переход на видео и ссылка из
карточки трека. Разные камеры/локальные треки и пробелы больше 0.5 с не соединяются.
Позиция человека рисуется только возле текущего наблюдения (не старше 0.25 с).
Вне многоугольника калибровочных точек координаты не экстраполируются.

Это ручная приблизительная проекция, **не метры и не 3D**. Качество зависит от
правильных соответствий, дисторсии камеры и видимости ног. Низкая ошибка подгонки
по четырём точкам сама по себе не доказывает точность привязки. Автоматическое
определение соответствий из одного рисунка расположения камер не реализовано.
Привязка не меняет результат ассоциации и не назначает ID.
При замене изображения плана старые привязки сбрасываются.

API:

- `PUT /api/datasets/{id}/floorplan/calibration/{camera_id}`: массив
  `{video:[u,v],plan:[x,y]}`, все координаты нормализованы в 0…1.
- `GET /api/datasets/{id}/frame/{camera_id}?time=0`: JPEG кадра.
- `GET /api/datasets/{id}/floorplan/trajectories?start=0&end=30&global_id=7`:
  точки с исходными camera/local/global ID, временем и x/y. Окно не более 120 с,
  максимум 10000 входных наблюдений; превышение отмечается `truncated`.
- `GET /api/datasets/{id}/floorplan` теперь также содержит сохранённые привязки.

Проверки проекции и API: `python -m pytest tests/test_floor_map.py tests/test_web_api.py -q`.
Проверены тип координат, нижняя точка bbox, сохранение идентификаторов, отсутствие
выдуманных точек без калибровки, ограничения области, сброс при замене плана.
Для экспорта видео с пятью камерами и картой:

```powershell
.venv/Scripts/python.exe -m pip install imageio-ffmpeg
.venv/Scripts/python.exe -m backend.export_review data/web/<dataset-id> runs/office_review.mp4 --seconds 10
```

Экспорт использует время и индивидуальный FPS каждой камеры. Алгоритм повторно
не запускается. Наблюдения, отображаемые ID и карта читаются из одного набора.

## Готовая демонстрация

Локальный набор: `86988f29-aa13-4991-9b99-2054f6ad51d1`, название
«Офис — трекинг 5 камер + приблизительная карта».
Результат: 981 наблюдение, 19 локальных треков, 17 итоговых ID; это число треков,
не подтверждённое число людей. На карту попали 658 наблюдений в области привязки.
В этом коротком прогоне ни один итоговый ID не объединил разные камеры. У человека
на размытых кадрах камеры 1 трек теряется; встречаются детекции изображений на ТВ.
Интерфейс показывает эти ограничения, алгоритм под красивую демонстрацию не менялся.

Видео: `runs/office_demo/office_tracking_10s.mp4`, 10 секунд, H.264, 1944×972,
10 FPS. Отдельный план: `runs/office_demo/office_map_4s.png`.
Проверены выбор G5 (Camera 4), G2 (Camera 2), воспроизведение карты и переход
к тому же времени и ID на видео. Привязка приблизительная, переносить её на другой
офис нельзя: для нового плана нужно заново задать соответствия.

Проверки: 85 Python-тестов, 2 Vitest-теста, 4 браузерных сценария без GPU-повтора;
production-сборка прошла. Финальное видео декодируется: 100 кадров при 10 FPS.
Веса, исходники видео, карта офиса и результаты обработки остаются локально.
